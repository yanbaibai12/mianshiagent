# Operations Runbook

> Status: Active
> Updated: 2026-08-27
> Scope: Agent Platform v2 operational surface

## CI/CD

Release evidence must be generated by the repository quality-gate commands. A build, lint result or handwritten checklist alone is not release evidence. CI and Release coverage thresholds remain separate ratchets.

## Monitoring

`GET /api/system/status` exposes a safe authenticated summary. Restricted operators can use the existing metrics, alert and backup endpoints. There is no product operations dashboard.

Active alert delivery uses:

- `ALERT_NOTIFY_ENABLED=true`
- `ALERT_WEBHOOK_URL=<alert gateway>`
- `ALERT_WEBHOOK_TOKEN=<secret token>`
- `ALERT_MIN_SEVERITY=critical`
- `ALERT_DEDUPE_MINUTES=60`

Alert records must contain only alert keys, severity, destination host, send status and bounded error text.

## Agent Shadow API

The authenticated `/api/agent-shadow/*` endpoints are an internal inspection surface and are hidden from OpenAPI. They are enabled only with:

```env
AGENT_SHADOW_API_ENABLED=true
```

Rules:

1. keep the flag `false` in production;
2. every create call requires `Idempotency-Key`;
3. the runtime reads only resources owned by the authenticated user;
4. cross-user and nonexistent resources produce the same public failure shape;
5. responses never expose raw internal state, request fingerprints, idempotency keys or complete Tool results;
6. local defaults to `AGENT_RUN_STORE_BACKEND=memory`; controlled PostgreSQL shadow evaluation uses `AGENT_RUN_STORE_BACKEND=postgresql` after migration `0018`;
7. PostgreSQL Run persistence does not imply worker durability: the endpoint still executes synchronously and recovery starts from the last committed checkpoint after lease expiry;
8. production release checks treat an enabled flag as critical.

See [`AGENT_SHADOW_API.md`](./AGENT_SHADOW_API.md) for the operator contract.

## Redis, PostgreSQL And Qdrant

Production requires external durable services rather than embedded fallback:

- `TASK_QUEUE_BACKEND=redis_rq`
- `TASK_ALLOW_LOCAL_FALLBACK=false`
- PostgreSQL at the current Alembic head
- `VECTOR_STORE_BACKEND=qdrant`
- a real embedding provider; hash embedding is not production quality

The Agent Shadow Runtime can persist Run state in PostgreSQL with `AGENT_RUN_STORE_BACKEND=postgresql`. It still does not dispatch Agent execution through Redis/RQ. Do not infer forced-process recovery, duplicate-delivery safety or production durability from database persistence alone.

## Backups And Recovery

Local SQLite backup endpoints are development aids. Production PostgreSQL requires managed snapshots/PITR and a recorded restore drill. Phase 1B cannot close until upgrade, rollback and restore are executed against a real PostgreSQL environment.

## Blue/Green And Canary

Use `DEPLOYMENT_COLOR`, `RELEASE_CHANNEL` and `CANARY_PERCENT` to label deployments. Canary values must remain between 0 and 100. Agent promotion additionally requires a rollback switch and shadow comparison evidence.

## Incident Minimums

For an Agent-related incident:

1. disable `AGENT_SHADOW_API_ENABLED` or the future Agent route flag;
2. preserve request IDs and sanitized Run IDs;
3. do not copy resume/JD/answer bodies into tickets;
4. classify authorization, factuality, durability and provider failures separately;
5. rerun the relevant quality gate after remediation;
6. record residual risk and recovery evidence.

Payment, package administration, organization administration and user quality-feedback operations are retired product responsibilities and are not part of this runbook.
